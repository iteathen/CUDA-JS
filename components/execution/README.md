# Bounded module launch and completion

The internal `runtime.execution` component implements the accepted CJS-F5W control-plane contract plus bounded follow-ups SPEC-0011, SPEC-0016, and SPEC-0018. It copies and identities bounded PTX/cubin, validates exact function parameter schemas, packs naturally aligned launch parameters, leases every device-memory argument through terminal completion, and owns opaque logical GPU operations over a fixed private stream pool.

SPEC-0016 separates submission from completion without widening concurrency. `submit()` returns only after launch and private event-record provenance exist. Later `operationStatus()` calls query the event once per short owner turn; terminalization destroys the private event, releases execution leases exactly once, stores terminal state, and frees the one-operation admission slot. Pending close is busy rather than cancellation, and runtime close may poll only inside its bounded close protocol. If terminality cannot be proved, dependency teardown is refused and restart-required/orphan truth is preserved.

SPEC-0018 adds an opt-in `maxPendingGpuOperations: 2` profile; the default remains `1`. The widened profile has exactly two private nonblocking streams and no hidden queue. Every device-memory argument requires one finite `accesses` declaration. Ordinary overlapping conflicts reject unless `after` names the exact earlier operation, in which case the successor is submitted on the predecessor stream and inherits CUDA stream order. Independently meaningful `u32`/`u64` relaxed device-scope atomic observation/update overlap is admitted on separate streams without an artificial dependency. A third submission receives typed backpressure. Unattributable deferred failure while multiple operations are pending conservatively orphans all of them and requires restart.

The launch parameter-kind set includes opaque `device-memory`, direction-specific SPEC-0014 `publication-mailbox-*-u32` lane capabilities, and the accepted scalar kinds. Mailbox lanes pack as private eight-byte mapped addresses only after the mailbox owner validates direction, generation, and exclusive operation lease. `u64` requires an exact JavaScript `bigint`; `i32` and `u32` use bounded integer `number` values; `f32` accepts finite numbers that do not overflow binary32. Packing is naturally aligned with deterministic zero padding and exposes no arbitrary C type or raw parameter-buffer contract.

The component has no direct Driver, FFI, or platform dependency. The DriverActor injects an exact Windows CUDA adapter or a portable orchestration mock. Legacy terminal `launch()` compatibility is orchestrated above the serialized actor command boundary as submit plus repeated short status turns; the DriverActor no longer remains inside one polling command for the full kernel lifetime. The mock proves policy, packing, lifetime, operation state, timeout, and teardown behavior only; it does not establish native CUDA ordering or qualification.

Accepted SPEC-0020 adds a kernel-only prepared-DAG resource without creating a second scheduler. The pure `runtime.prepared-execution` owner canonicalizes topology, binding schema, bounds, and identity; this component leases referenced functions, resolves each replay's scalar/memory/view bindings, rejects concrete unordered alias hazards before backend work, submits canonical topological order on one private stream, and represents the entire replay with one existing operation and one final event. Partial submission is restart-required. CUDA Graph realization, transfer/library/mailbox nodes, native qualification, and performance claims remain outside this baseline.

Stream/module registration and pre-submission event rollback never discard either the primary semantic failure or a later cleanup failure. Their bounded sanitized combined error includes both records, strongest resulting health, and unproved inventory. Failed cleanup of native ownership that was never registered is stored in an owner-local ledger, blocks further native creation, and is rethrown by close preparation so a later registry-only cascade cannot erase the first divergence. If GPU failure is already terminally observed but private event cleanup also fails, the logical operation remains orphaned with the same combined product and restart-required admission consequence.

Run `npm run f5:unit` for owner tests and `npm run f5:portable` for the platform-neutral integrated capsule.

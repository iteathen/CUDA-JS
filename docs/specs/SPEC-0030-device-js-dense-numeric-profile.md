# SPEC-0030: Device-JS dense numeric profile

**Status:** Accepted

**Version:** SPEC-0030-v1

**Owner:** `runtime.device-js`, consuming `runtime.compiler-actor` header profiles and the existing execution ABI

**Parents:** SPEC-0006, SPEC-0009, SPEC-0013, SPEC-0021, SPEC-0028

## Purpose

Add one bounded, consumer-neutral Device-JS numeric profile so the `f64`, `f16`, and `bf16` kinds already admitted by the public scalar ABI and typed device views can be used in generated device programs. The profile also supplies exact conversion and special-value helpers needed by unrelated numerical consumers without adding tensor, neural-network, training, search, or application policy to CUDA-JS.

The profile is additive. A request that uses only the pre-SPEC-0030 language retains the exact legacy Device-JS contract, identity and generated bytes. A request enters the dense profile only when its metadata or source uses a SPEC-0030 type or helper.

## Critical assessment and disposition

The strongest credible failure is a superficially portable half/bfloat implementation whose arithmetic, rounding or NaN behavior silently differs from CUDA, or whose headers come from an ambient toolkit path outside compiler identity. Reimplementing binary16/bfloat16 in consumer code, embedding CUDA source in a tensor package, or approximating them with `f32` all export hidden complexity and break the public-contract boundary.

The selected design uses the pinned CUDA 13.3 `__half` and `__nv_bfloat16` definitions and named round-to-nearest-even intrinsics through manifest-verified virtual header profiles. Device-JS owns the language semantics and private lowering; CompilerActor remains the only provider/header/cache owner. This is the smallest design that is exact, composable with existing CCCL atomics, removable with the first consumer, and independently qualifiable.

## Contract selection and compatibility

The dense program contract is:

```text
SPEC-0013-v1
+SPEC-0022-atomic-observation-v1
+SPEC-0022-device-publication-v1
+SPEC-0014-publication-mailbox-v1
+SPEC-0030-dense-numeric-v1
```

Dense libraries append the existing `SPEC-0028-device-library-v1` composition contract. Metadata containing `f64`, `f16`, `bf16`, or pointers to those kinds selects the dense contract. The new exact-cast, special-constant, absolute-value, NaN-classification, or NaN-propagating min/max helpers also select it.

Unchanged legacy requests retain their previous contract string, program/library identities, generated names and generated CUDA bytes. Dense and legacy library records are distinct copied values; facade validation accepts both exact contracts and never guesses from an artifact.

## Types and ABI

The accepted scalar set becomes:

```text
bool u32 i32 u64 f32 f64 f16 bf16
```

The accepted numeric set excludes `bool`. Pointer forms exist for every scalar kind. Local values, pointer loads/stores, same-unit device function parameters/returns, typed library exports/imports and kernel parameters admit the new kinds. Kernel scalar kinds reuse the exact SPEC-0021 execution packers; pointer arguments continue to use opaque device-memory/view capabilities.

Private CUDA lowering is exact:

| Device-JS | Private CUDA C++ | Width / alignment |
|---|---|---|
| `f64` | `double` | 8 / 8 |
| `f16` | `__half` | 2 / 2 |
| `bf16` | `__nv_bfloat16` | 2 / 2 |

The translator never exposes those CUDA names. New floating kinds do not gain atomics. Existing atomic helpers remain restricted to their accepted pointee kinds and scope/order profiles.

## Trusted numeric headers

CompilerActor adds two path-free manifest-owned profiles:

- `cuda-numeric`: the exact finite CUDA 13.3 top-level dependency closure needed by `cuda_fp16.h` and `cuda_bf16.h`;
- `cuda-device`: the exact union of `cuda-numeric` and the accepted `cuda-cccl` `cuda/` and `nv/` virtual roots.

Each component is independently inventoried before cache lookup. The composite identity hashes its ordered component identities and rejects duplicate logical header names. Caller headers may not shadow any owned root or exact logical file. No ambient include path is searched.

If a dense request omits `compile.headerProfile`, Device-JS selects `cuda-numeric`, or `cuda-device` when the same request also uses a scoped atomic/mailbox helper. An explicitly supplied profile must contain every required capability or translation fails before compiler work. Legacy atomic-only requests retain the existing explicit-profile requirement.

The first provider profile is exact CUDA 13.3. All policy-admitted `compute_75` or later targets may compile the semantic profile when that provider admits the target. This is not a claim of native half/bfloat acceleration; provider, architecture and performance qualification remain separate.

## Constructors, literals and exact casts

`gpu.f64(x)`, `gpu.f16(x)` and `gpu.bf16(x)` are typed constructors. Numeric literals are interpreted first as exact JavaScript binary64 values and then converted to the destination using round-to-nearest-even. Signed zero is retained. NaN and infinity literals remain unavailable through ordinary JavaScript syntax; typed special helpers provide them.

`gpu.cast.<kind>(x)` supports `u32`, `i32`, `u64`, `f32`, `f64`, `f16`, and `bf16` destinations and requires one already typed scalar expression. Its contract is:

- integer to integer: modulo destination width, with `i32` interpreted as two's-complement;
- integer to floating: round-to-nearest-even;
- floating to floating: round-to-nearest-even, preserving signed zero and infinity and producing a NaN;
- floating to integer: truncate toward zero then saturate to the destination range; NaN becomes zero and infinities clamp.

Legacy constructors retain their existing lowering for requests that do not select SPEC-0030. Consumers that require the exact cross-kind contract use `gpu.cast.*`.

## Arithmetic and comparison

Same-type `+`, `-`, `*`, `/`, compound forms and ordered comparisons admit `f64`, `f16`, and `bf16`; unary negation admits all signed floating kinds. `%` and bitwise operations remain integer-only.

`f64` uses ordinary CUDA double operations. `f16` and `bf16` use the CUDA 13.3 scalar round-to-nearest-even intrinsics (`__hadd_rn`, `__hsub_rn`, `__hmul_rn`, `__hdiv`, and `__hneg`) rather than implicit promotion. Results therefore round to the declared dtype after each operation. No fast-math, reassociation, contraction, tensor-core or performance policy is implied.

Comparisons are ordered: every ordered comparison with NaN is false and `!==` is true. Signed zeros compare equal.

## Math and special values

Typed zero-argument constants are:

```text
gpu.f32.nan()                 gpu.f64.nan()
gpu.f32.positiveInfinity()    gpu.f64.positiveInfinity()
gpu.f32.negativeInfinity()    gpu.f64.negativeInfinity()
gpu.f16.nan()                 gpu.bf16.nan()
gpu.f16.positiveInfinity()    gpu.bf16.positiveInfinity()
gpu.f16.negativeInfinity()    gpu.bf16.negativeInfinity()
```

They emit canonical quiet NaNs and exact signed infinities for the declared dtype.

`gpu.math.sqrt`, `log`, and `exp` retain byte-identical `f32` lowering and additionally admit `f64`, `f16`, and `bf16`. `gpu.math.abs(x)` admits every numeric kind; unsigned values are unchanged and `i32` uses two's-complement modulo behavior for its minimum. `gpu.math.isNaN(x)` admits floating kinds and returns `bool`.

Existing `gpu.math.min/max` preserve numeric-min/max behavior: one NaN operand yields the numeric operand. New `gpu.math.minimum/maximum` propagate NaN. For equal signed zeros, minimum returns negative zero and maximum returns positive zero. Integer forms are exact ordered min/max.

## Bounds, failures and ownership

All existing source, function, parameter, AST depth/count and import/export bounds remain unchanged. Dense-header selection is finite and provider-manifest-owned. Unsupported type/helper combinations, incompatible explicit profiles, wrong arity, float remainder/bitwise use, new-kind atomics and invalid function metadata reject in Device-JS before native work.

Device-JS remains pure preprocessing and owns no native resource. CompilerActor owns header snapshot/provider/program/link/cache resources. DriverActor and execution retain their existing context, module, function, argument, operation and cleanup ownership.

## Evidence and qualification

Portable acceptance requires:

- byte and identity fixtures for unchanged legacy programs and libraries;
- positive/negative/mutation coverage for every new type, pointer, constructor, cast, operator and helper family;
- exact header-profile default/conflict/cache identity tests;
- dense local and leaf-library composition tests;
- two unrelated installed-package consumers using only public exports;
- first-consumer deletion and no tensor/application vocabulary in production owners.

Native promotion requires one exact installed-package public-path fixture containing mixed `f64`/`f16`/`bf16` pointers, locals, device calls, kernel scalars, casts, arithmetic, special values and math; an independently authored native oracle; exact provider/header/target/artifact identity; negative controls; and terminal zero-resource cleanup. Windows evidence qualifies only its recorded profile. Linux and other providers/targets remain unqualified until their unchanged native chains run on suitable physical hardware.

## Non-goals

Tensor shapes or operations, graph planning/fusion, neural inference/training, vectors/records/fixed arrays, complex numbers, FP8, new atomics, fast math, tensor-core selection, arbitrary CUDA types/calls/headers, ambient include paths, public generated source, or performance claims.

# Packaging

**Status:** Accepted F8W package boundary

CUDA-JS `0.1.0-alpha.18` is a public-manifest, versioned no-addon ESM package with a Node 26.1.0 minimum testing substrate, exact Node 26.7.0 evidence baseline, three explicit exports, immutable compatibility metadata, clean tarball install/uninstall evidence, unrelated synthetic consumers, and exact manifest-verified CUDA 13.3 provider/header profiles. Its additive surface includes typed relocatable PTX, scalar launch kinds through SPEC-0021, typed Device LTO, restricted Device-JS and its accepted atomic/mailbox children, typed Device-JS leaf-library composition, SPEC-0030 dense `f64`/`f16`/`bf16` scalar computation, the ordinary operation lifecycle, device selection/targets, contiguous typed views, SPEC-0020 semantic prepared kernel DAGs, one optional SPEC-0023/SPEC-0029 cuBLASLt f32 row-major matmul profile, SPEC-0031 bounded prepared composition of those plans, and public immutable projection of the already-owned finite prepared-DAG and Device-JS parameter ceilings plus the ordinary device-allocation minimum base-address alignment. Alpha.18 changes no allocation request, native allocation call, view-offset rule, or lifecycle; it exposes the accepted 256-byte ordinary base-allocation minimum through `cuda-js/compatibility` so upper planners can reject unsupported requirements before allocation without copying a native CUDA fact. `allocateDevice({ byteLength })` gains no alignment field, arbitrary nonzero-offset views receive no blanket 256-byte guarantee, and a requirement above the published minimum remains unsupported by this profile. The selected-runtime Device-JS target behavior introduced in alpha.16 remains unchanged: Device-JS translation/library/import identity and produced artifacts bind to the selected runtime target, and a conflicting explicit Device-JS target fails before compiler work. Dense requests use exact `cuda-numeric` or composite `cuda-device` headers without adding exports, tensor semantics, tensor-core policy, fast math, or performance claims. Prepared replay and library calls return existing operations; neither adds search, arbitrary native control, a public plug-in registry, or CUDA Graph claims. Provider discovery remains lazy. All additive capabilities retain exact profile gates. Device-JS uses pinned `acorn@8.15.0` only as a syntax parser; CUDA-JS owns its accepted grammar, semantics, types, lowering, identity, and CUDA compilation boundary. Structurally admitted native Windows x64 and Linux x64 profiles may operate for testing without a separate opt-in; Linux and later additive native profiles remain not-qualified unless exact evidence says otherwise. CUDA-JS source is AGPL-3.0-or-later with separately negotiated commercial licensing available. Registry publication remains pending a separate release, provenance, and registry review.

ADR-0007 assigns reusable NN semantics to the independent `iteathen/cuda-nn` repository and generic Tensor mathematics/planning to `iteathen/CUDA-JS-Tensor`. Historical ADR-0004/SPEC-0027 remain provenance for the superseded same-repository NN isolation plan but no longer authorize a CUDA-JS-owned NN package, workspace, export, dependency, compatibility identity, provider discovery, or import side effect. No CUDA-NN package or support claim is bundled with `cuda-js`; any future CUDA-NN consumption uses separately versioned public contracts and its own qualification.

Shared native engines now source-admit Windows x64 and Linux x64 through thin platform profiles. Windows retains exact accepted evidence; Linux x64 remains `testing-unconfirmed` and not-qualified pending native runners and exact installed-package evidence. Linux ARM64 remains backend-incomplete and WSL2 diagnostic-only. All profiles can install, import, inspect compatibility, and use the mock-only testing export; none gains a native CUDA claim from portable controls.
